# 离开电脑后还能找到 TA · 实施计划 v1（功能 7）

> 状态：2026-11-04 已按用户决定实现 R1（微信，直接对接腾讯 iLink）与 R2（主动研究 + 微信小报）。用户决定：通道只做微信；手机端是完整对话（带长期记忆、工具与任务）；内容全部推送不另设限制；发送额度以腾讯规则为准、不加设置。保留三条底线：只认扫码绑定的人、出站仍经 PrivacyGuard 脱敏、确认以编号回复。下文其余部分是原计划稿，飞书 / 企业微信 / Bark / ntfy 等通道未做。
> 依据：`AGENTS.md` 第 4 节红线、`docs/主动陪伴与上下文管理-v1.md`、`docs/活人感-v1.md`、`runtime/core/companion.ts` 现有实现。
> 标注“待核实”的是我不确定的第三方 API 细节，开工前要先查官方文档并在 R0 中实测。

## 1. 目标与非目标

**目标**
- 用户离开电脑（锁屏，或空闲超过 N 分钟）时，把**原本会在桌面上出现的一句话**用很短的通知推到手机上。
- MVP（R1）只做单向推送：
  1. **用户自己设的定时提醒**到点（`SelfWake.createdBy === 'user'`）；
  2. **“TA 有话想说”**：主动消息发出后 N 分钟没人回，用户也确实不在；
  3. **后台任务结束**：只推“已结束 / 未完成”，不带执行器输出。
- R2：从手机回复，**只能聊天**，外加几个只会让 TA 更安静的指令。

**非目标**
- 不为推送新增任何模型请求：推送文本要么是已经生成的台词，要么是固定模板。
- 不做中转服务器。**电脑必须开着且没睡眠**；关机或睡眠时什么都不会发，界面要写清楚。中转服务另有隐私问题，不在本计划内。
- 不新增任何观察能力；手机端不能派任务、改设置、跑 Shell。
- 不推送角色自己设的闹钟、早安/晚安、分享、旧事重提。这些都要求用户“在场”，见 `lifeBlocked` 里的 `!this.present()`。

## 2. 通道对比与推荐顺序

| 通道 | 内容经过谁 | 数据在境内？ | 收消息方式 / 要不要公网入口 | 国内可用 | 费用 | 备注 |
|---|---|---|---|---|---|---|
| 企业微信群机器人 webhook | 腾讯 | 是 | 只能发；无需入口 | 好 | 免费 | `POST qyapi.weixin.qq.com/cgi-bin/webhook/send?key=`；key 就是凭据。约 20 条/分钟（待核实）。建群人数下限待核实；群里所有人都能看到 |
| 企业微信自建应用 | 腾讯 | 是 | 收消息要公网 HTTPS 回调，还要已备案域名（待核实） | 好 | 免费 | 新应用调 API 可能要配“可信 IP”，家庭动态 IP 不好满足（待核实）。可以经“微信插件”在个人微信里收到 |
| 飞书群机器人 webhook | 字节（飞书境内版） | 是（Lark 国际版不是） | 只能发；可加签 | 好 | 免费 | `open.feishu.cn/open-apis/bot/v2/hook/…` |
| 飞书自建应用 | 字节 | 是 | 事件订阅支持“长连接模式”：只由电脑向外连，不开端口（待核实 Node SDK 用法） | 好 | 免费 | 是 R2 双向通道的国内首选 |
| Telegram Bot | Telegram（境外） | 否；bot 对话不是端到端加密 | `getUpdates` 长轮询，只由电脑向外连 | 需要代理 | 免费 | 双向最简单；内容会出境 |
| Bark（iOS） | 官方服务器 + Apple APNs，或自建 bark-server | 官方服务器位置待核实 | 只能发 | 好 | 免费 | 支持推送内容加密（AES，待核实参数）。只有 iOS |
| ntfy | ntfy.sh（美国）或自建 | 自建时由用户决定 | 发用 POST；订阅是向外的流式连接 | ntfy.sh 不稳 | 免费 | topic 名等于口令，知道就能读；没有端到端加密 |
| Server 酱 / PushPlus 等 | 第三方运营商 | 是 | 只能发 | 好 | 部分收费 | **不推荐**：内容会留在小厂服务器 |

**推荐顺序**
1. **R1 单向**：企业微信群机器人 → 飞书群机器人 → Bark → ntfy。四个都只发一个 HTTPS POST，共用同一套发送逻辑。
2. **R2 双向**：飞书自建应用（长连接）→ Telegram（长轮询，给能用代理、能接受内容出境的用户）。
3. **最后才考虑**：企业微信自建应用。它要公网回调和可信 IP，和“不在电脑上开端口”的原则冲突。

## 3. 隐私设计（核心）

### 3.1 内容分级（每个通道单独设置）

| 级别 | 推送内容 | 说明 |
|---|---|---|
| `ping`：只提醒有新消息 | `「{角色名}」有话想对你说` / `你设的提醒到点了` / `后台任务结束了` | 不带任何对话内容。可再选“连角色名也不带”，统一显示为 `GalAgent：有 1 条新消息` |
| `brief`：短通知（默认） | 台词第一段（`parts[0]`），最多 60 字；提醒取 `note`，最多 60 字 | 必须先过 `PrivacyGuard.pushText()` |

- **自动降级为 `ping`**：消息的 `initiativeTopics` 含 `screen / clipboard / window / browser` 任一项时。这类台词可能转述了屏幕、剪贴板、窗口或浏览器内容。
- 任务结束一律按 `ping` 处理：执行器的摘要和输出永远不推。
- 通道属于境外服务时（Telegram、ntfy.sh），界面默认推荐 `ping`。

### 3.2 永远不出本机

记忆、日记与每日档案、截屏与剪贴板摘要、窗口标题、浏览器内容、执行器的输出与文件路径、`brief()` 简报包、设置快照、隐私审计明细。推送模块**只读**以下数据：最终台词 `Message.text/parts`、提醒的 `note`、任务状态枚举。

### 3.3 必经 PrivacyGuard

在 `runtime/core/privacy.ts` 新增 `pushText(text, channel)`：
- 调用 `redactText` 时**强制**打开 `redactSecrets` 和 `redactPersonal`，并带上用户的 `sensitiveWords`；
- 不受沙箱“关闭脱敏”影响，因为手机通道比模型上游更容易泄露；
- 审计渠道记为 `push:<kind>`，只记类别和次数；
- 脱敏后如果只剩占位符，或命中 `private-key / api-key / credential`，整条降级为 `ping`。

### 3.4 密钥

- webhook URL、key、bot token、加签 secret、Bark 加密密钥，全部存进 `<userData>/remote-secrets.bin`。做法照抄 `runtime/main/index.ts` 里的 `mcpSecrets`：`safeStorage` DPAPI 加密，原子写入。
- 设置里只存 `secretSet: true`；渲染进程、SQLite、日志、报错文本里都不出现。报错只保留错误类别，不带 URL。
- 这个文件名要加进 `galagentSecret()` 和 `sensitivePath()` 的正则，任何沙箱级别下执行器都读不到。

### 3.5 只有用户能开

- `remote` 设置整体**只有用户能改**，`aiControl === 'full'` 也不行。做法：在 `control().updateSettings` 里，像现在删掉 `aiControl` 一样直接 `delete p.remote`；在 `settingsView` 里只暴露“是否已开启”。
- 理由：这是数据离开本机的新出口，不适合靠一张确认卡放行。
- `privacy.lockdown` 一并把 `remote.enabled` 设为 `false`，中止发送队列和收消息的轮询。
- 托盘菜单加“暂停手机推送 1 小时 / 直到我恢复”，即时生效。

### 3.6 门控（发送前逐项检查）

| 检查项 | 规则 |
|---|---|
| 总开关 / 暂停 | `remote.enabled` 为真，且已过 `pausedUntil`，且通道已启用、密钥已设置 |
| 免打扰 | `quietUntil` 和 `inQuietHours()` 期间一律不推。另设开关 `remindersInQuietHours`（默认关），只放行用户自设的提醒 |
| 陪伴模式 | `rest` 模式什么都不推。`focus` 模式只推用户自设的提醒，与 `deliverSchedules` 的 `allowed()` 保持一致 |
| 话题开关 | `companionship.topics[t] === 'mute'` 不推；推送自己另有话题开关（提醒 / 有话想说 / 任务） |
| 频率 | 默认每小时最多 4 条、每天最多 12 条，按 `numericSettings` 收拢范围。10 分钟内的多条合并成一条（`TA 有 3 条新消息`） |
| 不在场 | 见 3.7 |

推送**不调用** `recordInitiative`，也不计入 `proactiveGate`：它只是转发已经说出口的话，不是新的开口。

### 3.7 怎么判断“不在电脑前”

复用现有观察数据，不新增采集。参照 `present()`，新增 `awayFor(now)`：
- 观察开启时：锁屏（`o.locked`）算不在；`idleSeconds ≥ awayMinutes*60`（默认 15 分钟）也算不在。`o.suspended`（睡眠）时本来就发不出去。
- 观察关闭时：无法判断，只推用户自设的提醒（界面写明）。也可以由用户打开“不管在不在都推提醒”。

### 3.8 来自手机的消息（R2）

- 一律当作**不可信的用户输入**。
- 配对：电脑上生成 6 位码，10 分钟有效，手机发 `/pair 123456`，把 `chat_id + user_id` 绑定进白名单。其他发送者一律丢弃，只记次数。最多绑定 1 个账号。
- 能做的事：普通聊天，以及只会更安静的指令 `/安静 2h`、`/暂停推送`、`/恢复推送`。
- 不能做的事：`run_task / update_settings / watch / cancel_task / undo_task`，联网工具，`schedule_wakeup`（R2 先不开）。手机端发起的聊天**拿不到** `control()`，需要新增 `activeKind = 'remote'`。
- 回复会被推回手机，所以手机端对话的上下文**默认不带长期记忆、观察、屏幕笔记、剪贴板和浏览器内容**，只带角色卡和最近的可见对话。否则 token 一旦泄露，别人就能从手机把记忆套走。
- 收消息限流：每 10 分钟最多 10 条，超出直接丢弃。
- 更危险的指令（派任务等）留到 R3 再议，前提是逐条在电脑端确认。

## 4. 架构

### 4.1 新增模块

| 文件 | 职责 |
|---|---|
| `runtime/core/remote/outbox.ts` | `Outbox.offer(item)`：去重 → 门控 → 合并 → 每个通道串行发送 → 重试 → 记账 |
| `runtime/core/remote/channels/*.ts` | `wecom-webhook / feishu-webhook / bark / ntfy`（R2 加 `telegram / feishu-app`），统一接口 `send(text, secrets, fetch, signal)` |
| `runtime/core/remote/inbound.ts`（R2） | 长轮询或长连接、配对、白名单、限流，转成 `remote.inbound` |

- **请求方式**：`fetch` 通过 `CompanionOptions.remoteFetch` 注入。桌面端用 Electron `net.fetch`，以便走系统代理（Telegram 要用；待核实现有上游是否已经这样做）。测试里换成假的 fetch。
- **地址白名单**：每种通道的主机写死（`qyapi.weixin.qq.com`、`open.feishu.cn`、`api.day.app`、`ntfy.sh`、`api.telegram.org`）。只有 Bark 和 ntfy 允许自建地址，且必须是 HTTPS，DNS 解析出的地址要过 `tool-host.ts` 的 `isPrivateAddress` 检查。
- **不占 20 路并发池**：并发池是给 K3 模型请求用的。推送单独排队，每个通道并发 1。重试复用 `upstream.ts` 的 `backoffMs` 和 `retryAfterMs`：最多 3 次，单次超时 10 秒；只重试网络错误、429 和 5xx。企业微信、飞书会在 HTTP 200 里返回 `errcode` 或 `code`，要按各自的错误码判断（待核实具体码值）。
- **去重**：键为 `reminder:<id>:<dueAt>`、`message:<id>`、`task:<runId>`，持久化保存最近 300 个已发送的键。排队中的推送正文只放在内存里，重启后丢弃，不落盘。

### 4.2 接入点（`runtime/core/companion.ts`）

1. **提醒**（`deliverSchedules`）：现在用户锁屏时，`attentionBlocked()` 返回 `'locked'`，提醒会一直等到解锁。改法：在 `allowed()` 判断之前，对 `createdBy === 'user'` 且已到点的提醒，如果 `awayFor()` 成立，就 `outbox.offer({kind:'reminder', key, text: note})`，**不发模型请求**。用户回到电脑后，桌面端照常让角色把提醒说出来；去重键保证手机不会收到第二次。
2. **有话想说**：`generate()` 保存了 `kind==='initiative'`、正文非空的消息后，登记一个延时检查（`unansweredPushMinutes`，默认 10 分钟）。到时如果这条仍是最后一条、用户没回、而且仍然不在场，就 offer。这与 `checkUnanswered`（它要求用户在场）互为补充。
3. **任务**：在 `taskEvent()` 里，如果用户不在场，就 offer 一条 `ping`。
4. **R2 回复**：`remote.inbound` 先过白名单和限流，再调用 `send(text)`，走 `activeKind='remote'` 的精简上下文。回复保存时带 `Message.via='remote'`，然后推回手机。手机回复要算作 `pacing` 的“已回应”，但不算“在电脑前”。

### 4.3 设置与快照（`runtime/shared/contracts.ts`）

```ts
remote?: {
  enabled: boolean; pausedUntil: number;
  channels: { id: string; kind: RemoteKind; name: string; enabled: boolean;
              contentLevel: 'ping' | 'brief'; hideName?: boolean; server?: string; secretSet: boolean }[];
  awayMinutes: number; unansweredPushMinutes: number; hourlyLimit: number; dailyLimit: number;
  topics: { reminder: boolean; initiative: boolean; task: boolean };
  remindersInQuietHours: boolean; remindWhenUnknown: boolean;
  inbound?: { enabled: boolean; paired?: { channelId: string; label: string; pairedAt: string } }; // R2
}
```

- **快照** `remote`：每个通道的 `lastOkAt`、`lastErrorKind`、`sentToday`；`pausedUntil`；配对中的倒计时（R2）。不包含任何正文。
- **命令**（`runtime/main/validation.ts` 逐条校验）：`remote.secret`（通道 id 和密钥键名白名单，值 ≤ 4000 字符）、`remote.test`（发一条固定测试文本）、`remote.pause`、`remote.pair`、`remote.unpair`、`remote.inbound`（仅主进程内部使用，渲染进程不能发）。
- **默认值**：`enabled: false`。在 `defaults` 和 `numericSettings` 里加上对应字段和收拢范围。
- **界面**：设置页新增「离开电脑时」分区。内容包括：通道列表、添加向导（每种通道一步步引导）、内容级别、测试按钮、“哪些内容会离开电脑”说明卡、暂停按钮、今日已发条数。

## 6. 测试计划

**单元测试**：新增 `tests/core/remote.test.ts`，并在 `companion.test.ts` 里补用例，统一注入假 fetch 和假时钟。

| 用例 | 断言 |
|---|---|
| 提醒推送 | 锁屏时到点的用户提醒只推一次，没有模型请求；解锁后桌面照常提醒；角色自设的闹钟不推 |
| 有话想说 | 无人回应、超时且不在场才推；期间用户回复或回到电脑则取消 |
| 脱敏 | 正文含 `sk-…`、手机号、身份证号、自定义敏感词时都被替换；沙箱关了脱敏也照样替换；命中密钥类时降级为 `ping` |
| `ping` 模式 | 请求体里找不到原台词中的任何片段（逐字比对） |
| 话题降级 | 带 `screen / clipboard` 话题的台词只发 `ping`；任务只发状态 |
| 门控 | 免打扰、`rest`、`focus`、话题静音、暂停、lockdown、每小时 / 每天上限、合并 |
| 重试 | 429 带 `Retry-After`、5xx 退避、4xx 不重试、企业微信 200+errcode；报错和快照里不出现 URL 或 key |
| AI 不能改 | `update_settings({remote:…})` 无效，`settingsView` 不暴露密钥 |
| 地址 | 自建地址是内网或 http 时拒绝 |
| R2 | 白名单外的发送者被忽略；配对码过期失效；手机端请求的 tools 里没有 `run_task` 等；上下文不含记忆和观察；限流 |

**手动验收（Windows）**
- 企业微信 / 飞书 / Bark 真机各收一条；
- 锁屏 20 分钟收到提醒，解锁后不重复；
- 托盘暂停和一键锁定立即生效；
- 断网后恢复，确认会重试但不轰炸；
- 检查 `%APPDATA%/GalAgent` 下只有加密的 `remote-secrets.bin`，日志里没有 key；
- 用 Wireshark 或代理抓包，确认只连了白名单里的主机；
- 睡眠和关机时不发送，界面有说明。

## 7. 里程碑、风险与待决问题

| 阶段 | 内容 | 粗估 |
|---|---|---|
| R0 | 核实各“待核实”项：企业微信建群人数和频率、自建应用的可信 IP、飞书长连接、Bark 加密、`net.fetch` 走代理 | 0.5–1 天 |
| R1 | Outbox、四个单向通道、`pushText`、密钥存储、门控、界面、单元测试、AGENTS.md 修改 | 4–5 天 |
| R2 | 飞书应用长连接与 Telegram 双向、配对、`activeKind='remote'`、精简上下文 | 4–5 天 |
| R3 | Windows 实机验收与 soak 测试，更新 NEXT.md 和 CHANGELOG | 1–2 天 |

**风险**
- 第三方平台会留存推送内容（尤其企业群可能被管理员审计、Telegram 在境外）。缓解：`ping` 档、境外通道默认推荐 `ping`、界面明示。
- webhook key 泄露后别人能冒充 TA 给你发消息，但读不到你的数据。可以随时在平台上重置。
- 观察关闭时判断不了在不在场，体验会打折扣。
- 双向通道 token 一旦泄露，等于开放一个聊天入口。缓解：配对白名单、上下文不带记忆、限流、一键解绑。
