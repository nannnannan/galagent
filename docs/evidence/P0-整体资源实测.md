# P0：整体资源与实际记忆管线

当前结论：默认 ONNX 嵌入方案在运行时明显超过总设计案的 **800 MiB 全项目峰值** 目标。固定线程减少 CPU 竞争，45 秒空闲卸载已实测有效，但首次模型加载与规模检索峰值仍超预算；不能用单独 Node 模型开销宣称整项目达标。

## 口径与复现

`node --expose-gc --import tsx scripts/probe-runtime-resources.mjs`

真实 `CompanionService` 使用独立 `.cache/resource-probe-data/<timestamp>-<variant>`，credentials 返回 undefined，离线模型路径 `.cache/models/Xenova/multilingual-e5-small`。不会生成任何真实模型聊天请求。3 次 `memory.remember` → `await waitForBackground()` → `retrieve` 经过实际消息来源、memory、FTS、向量 DB、后台队列与混合排序。测试内容均为编造事实，不写入用户实际存档。

运行中的桌面 app 保持打开，没有更改观察/标题隐私开关，没有关闭或重启现有 app。PowerShell `Get-CimInstance` 仅筛选项目路径及其子进程，`Get-Process` 只输出 PID、类目、工作集、私有内存和 CPU 秒；不输出命令行或外部 app 信息。后续脚本显式补查 project `observer.ps1` helper，排除临时采样 PowerShell。基线采样未见 observer helper。

项目采样含 dev Node helpers；进程工作集求和可能重复计入共享页面，私有内存另列。替身 Node 是额外验证进程，它的合计不是已经部署进 app 后的精确内存；但其增量与现有 Electron 基线足以指出明显预算风险。最终应在打包后的 app 内触发真实索引再测全部项目进程。

3 个后台索引任务均 `done`，embedding=`ready`；查询“周末会做什么运动？”首位为游泳，查询 11.17 ms。记忆写入、后台处理及查询约 2.19 秒，累计 CPU 4.094 秒（多线程 CPU 累计会超过墙钟）。状态轨迹从 idle/queued 到 loading/running 再 ready/done，没有本轮 `waitForBackground` 提前返回的问题。

### 10k Store 规模

创建 10,000 个独立合法 UUID 的 source Message + Memory，`Store.put/index/vector` 在事务写入；每条文本带不同容量编号，向量重复使用一条**真实模型生成的 384 维向量**。这是实际数据库规模压力，**不是 1 万条真实语料嵌入或召回质量测试**。没有把相同向量的排序当作语义质量。

| 指标 | 默认基线 |
|---|---:|
| synthetic 索引写入 | 23,932 ms |
| DB 体积 | 91,754,496 bytes |
| 服务记忆总数 | 10,003 |
| 首次查询（含重载模型/构建缓存） | 2,810.55 ms |
| 20 次热查询均值 | 93.52 ms |

热查询低于 150 ms 目标；索引峰值与真实进程总内存未达预算。没有以热扫描或热查询证明冷启动和峰值达标。

## 限制线程对照

`--threads1` 注入同样的 feature-extraction/q8/mean/normalize/query-passsage pipeline，只将 `intraOpNumThreads` / `interOpNumThreads` 设为 1，工作仍在独立 worker。3 条记忆的真实管线比较：

| 指标 | 默认 | 限制 1 线程 |
|---|---:|---:|
| 索引与首次查询 | 2.19 秒 | 1.62 秒 |
| 累计 CPU | 4.094 秒 | 2.469 秒 |
| 热查询 | 11.17 ms | 12.30 ms |
| 加载模型 Node 工作集 | 614.45 MiB | 611.18 MiB |

限制线程适合减少后台竞争，内存差异仅约 3 MiB，不能解决模型主开销。

**被废弃的子结果**：threads1 运行期间 core 正在调整恢复状态，第二服务导入了 init 不设 ready、retrieve 仍 gated ready 的中间版本；10k 阶段没有重新加载模型，成为仅 FTS。结果 JSON 保留该记录与源文件 hash 作为诊断证据，其 10k 时间/内存不能用作完整语义策略改善结论。发现后已向 core/主代理报告，并在稳定代码后重跑 `--idle`。

## 新版：2 线程、45 秒 idle、streaming 向量

北京时间 2026-10-09 凌晨新进程实测，完整 `runtime-resources-threads2-idle.json` 记录源文件 hash。测试进程已导入 READY 的 CompanionService 与 Embeddings；运行期间 worker 后续增加 dispose 消息处理，但没有改变模型/线程/向量参数。最新 dispose 版本另以独立 `default-short` 进程完成真实索引、40 次查询与关闭 smoke。

| 场景 | 服务 Node RSS | 项目+验证进程工作集 | 结果 |
|---|---:|---:|---|
| 3 条记忆索引、检索 | 641.31 MiB | 1,249.74 MiB | 全任务 done，ready，命中游泳 |
| 等待 52 秒 + GC | 65.78 MiB | 674.72 MiB | embedding idle，向量仍在 DB |
| idle 后再次 retrieve | 611.57 MiB | 1,220.51 MiB | 重载 1,947.54 ms，ready，命中游泳 |
| 10k streaming 实际检索 | 754.03 MiB | 1,363.03 MiB | 完整语义 + FTS |
| 10k 服务关闭 + GC | 424.24 MiB | 1,033.25 MiB | 短时快照，不是 45 秒闲置结论 |

新版 10k 首查 3,052.21 ms，20 次热查询 mean 115.96 ms / p95 123.43 ms / max 124.24 ms，仍低于 150 ms。Node 峰值 756.09 MiB，比旧 1,000.70 MiB 降低约 244.61 MiB；这是 streaming 向量读取等代码组合的实测改善，不归因于单个未经隔离的改动。**全项目峰值仍未通过 800 MiB**。

空闲后 RSS 接近加载前 Node 基线证明资源回收有效；复热时 RSS 上升和 ready 状态证明没有退化为 FTS-only。复热耗时约两秒需 UI 的加载反馈，不假称始终即时响应。

## ONNX 配置额外探针

全部只在专用 probe 注入，未修改生产配置。来源与进程结果见相应 `*-short.json`。

| 配置（其余 q8/CPU/2线程相同） | 3 记忆时工作集 | 私有内存 | 40 次同一热查询 p95 |
|---|---:|---:|---:|
| 最新生产默认 | 615.48 MiB | 842.58 MiB | 7.91 ms |
| 禁用 graphOptimizationLevel | 610.25 MiB | 731.56 MiB | 10.55 ms |
| 同时禁用 CpuMemArena + MemPattern | 618.19 MiB | 649.20 MiB | 未采集 |

图优化单变量仅减少约 5 MiB 工作集，并增加查询延迟；私有内存下降约 111 MiB。禁 arena/pattern 是两个关联选项的联合探针，不能拆开归因；它降低私有内存而没有改善工作集。两者都仍有约 1.2 GiB 项目+验证进程合计，**不足支持直接采用，也不足解决当前目标**。这 40 次重复同一查询是延迟 smoke，不是 40 条不同语义质量样本；语义质量仍以先前固定 20 事实/40 不同查询报告为准。

## 策略与后续检查

1. ONNX 默认 1–2 线程：减少抢占 UI；不要宣传成大幅降低模型内存。
2. 45 秒无 pending 自动卸载 worker：保留向量数据库与缓存，下次查询复热；UI 表示 idle，而不是把有向量等同于模型常驻 ready。恢复检索应根据存在向量判断，不能只 gated ready，否则卸载后悄悄退化成关键词查询。
3. worker 终止不一定把全部 native allocator 内存返还 OS。若 45 秒后 RSS 仍大，考虑独立按需 Node 子进程，退出获得更明确的完整资源回收；保留 IPC 串行队列、超时/取消/有限重启，不创建每 query 一个进程。
4. 对 10k 索引，DB JSON 向量转一次 Float32Array 的内存峰值需要专门控制；建议 DB 二进制向量或逐行迭代建立缓存，避免 `SELECT *` 全结果 JSON + number[][] 同时存在。改造后必须复测整个 app。

本轮未做 10 分钟静置、48 小时稳定性、重启后的磁盘冷加载或打包 app 内索引峰值，因此这些验收项仍待验证。
